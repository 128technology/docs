When you downgrade an SSR router to a release that cannot parse `auto` in an application-identification setting, the router may fail to load its configuration.

<!-- truncate -->

**Issue ID:** I95-66708
**Last Updated:** 2026-10-22
**Introduced in SSR Version:** Version-dependent by application-identification field
**Resolved in SSR Version:** 7.0.6, 7.1.8, and 7.2.5

## Symptom

After a downgrade or rollback, the router fails to load or apply its configuration. The logs may include an error similar to:

```text
ConfigException: Config field could not be coerced/retrieved:
  router..application-identification
Non-digit character found: 'auto'
```


## Cause

Some application-identification capacity and cache settings accept `auto`, which lets SSR select a value automatically. The settings include:

- `application-identification.application-director-cache-max-capacity`
- `application-identification.web-filtering.classify-session.max-cache-size`

Support for `auto` varies by field and SSR release. If the configuration contains `auto` for a field that the downgrade target only accepts as a number, that release cannot parse the configuration and rejects it. In an HA deployment, the two nodes can run different releases during a node-by-node downgrade while receiving the same configuration.

SSR populates these settings with `auto` by default starting in the below version matrix. You may therefore find `auto` in the configuration even if you did not explicitly configure it.

An upgrade to a release that supports `auto` can introduce these values into the configuration. If you later revert or roll back to a release that predates support for the affected field, that older release may fail to load the configuration.

### Version Compatibility

The following release-line thresholds identify older rollback targets that may not parse `auto`:

| Release line | `auto` support starts in | Rollback targets that may fail |
|---|---|---|
| 6.2 | 6.2.11 | 6.2.0-6.2.10 |
| 7.0 | 7.0.5 | 7.0.0-7.0.4 |
| 7.1 | 7.1.6 | 7.1.0-7.1.5 |
| 7.2 | 7.2.0 | None listed |

These are release-line thresholds; the first release supporting `auto` can vary by field. Before rolling back, verify support for each affected field in the target release.

## Workaround

Before downgrading, check the router's application-identification configuration:

```text
show config running authority router <router-name> application-identification
```

For each listed field set to `auto`, replace it with an explicit numeric value supported by both the current release and the downgrade target. As starting values, use `10000` for `application-director-cache-max-capacity` and `150000` for `web-filtering.classify-session.max-cache-size`, if those capacities are appropriate for your platform. Otherwise, use values you have validated for your router. Commit the change and confirm that it has synchronized to both HA nodes before proceeding.

After the downgrade completes, the target release has loaded its configuration, and both HA nodes are synchronized, remove the temporary numeric overrides if you want the target release to use its defaults. Commit the change and verify that both nodes remain in service.

If a node has already failed to load configuration after a downgrade, apply the correction from the conductor, or directly on the node if it is reachable, then commit and allow the node to synchronize.

## Resolution

The issue is fixed starting in SSR 7.0.6, 7.1.8, and 7.2.5. Upgrade to the corresponding fixed release before relying on corrected rollback behavior in those release lines.

When downgrading to an earlier release, replace `auto` with numeric values that the target supports before starting the downgrade. The fixed releases listed here do not specify a 6.2 correction; use the workaround when a 6.2 release is involved and confirm target-release compatibility for each field.
